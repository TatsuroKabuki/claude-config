# オーケストレーション方針（全リポジトリ共通）

> **正本は claude-config リポジトリ（このファイルを含む submodule の取得元）。** 各リポジトリは `.claude/agents` に git submodule として取り込み、`CLAUDE.md` から `@.claude/agents/rules/orchestration.md` で import する。直接編集せず、正本を直して push → 各リポジトリで submodule ポインタを更新する。
> リポジトリ固有のルール（対象アプリの判定・コマンド・規約・git 運用）はここに書かない。各リポジトリの `CLAUDE.md` / `AGENTS.md` / `CODING_GUIDELINES.md` が権威で、それらと食い違う場合はリポジトリ側が優先する。

## 0. 環境の判定（ローカル / Claude Code on the web）

環境によって使える委譲先が違う。**着手前に 1 度だけ判定し、以後の委譲はその結果に従う。**

| 判定材料 | ローカル | web |
|---|---|---|
| Agent ツールの利用可能一覧に `codex:codex-rescue` がある | あり | なし |
| `~/.claude/` のユーザースコープ設定 | 読まれる | 読まれない |
| `/config` | 使える | 使えない（`/model sonnet` のように引数形式で指定） |

- `codex:codex-rescue` が一覧に**あれば** Codex が使える環境（§2-A）。**なければ** Claude 内で完結する環境（§2-B）。
- 判定結果を変える操作（プラグインの追加など）はしない。

## 1. エージェントと担当（`.claude/agents/`）

| エージェント | 担当 | 編集 | 既定モデル |
|---|---|---|---|
| `researcher` | 所在・原因特定・影響範囲・仕様確認 | しない | sonnet / high |
| `designer` | 設計・アーキテクチャ・トレードオフ。設計ドキュメントは書ける | 本番コードは触らない | fable / xhigh |
| `implementer` | 設計確定後の実装 + 検証 | する | opus / high |
| `reviewer` | 差分レビュー（correctness 最優先） | しない | opus / xhigh |

組み込みの `Explore` / `Plan` / `general-purpose` は、上の 4 つで表現できない単発の検索・並列 fan-out にだけ使う。**根本原因・影響範囲・設計・レビューは必ず上の 4 つに出す**（モノレポの対象判定と `path:line` 付き報告の規律が組み込みには無いため）。

## 2. 実装タスクのルーティング

### 2-A. Codex が使える環境（ローカル）

コード変更を伴うタスク（実装 / 修正 / リファクタ / テスト追加）は `codex:codex-rescue` に委譲する。`codex-rescue` は**転送専用**なので、差分確認・検証コマンド実行・`reviewer` でのレビューはオーケストレーターが担う。

委譲プロンプトに必ず含める:
- 対象アプリ / パッケージ（モノレポなら先に確定させる）
- 読むべきルール（最寄りの `CLAUDE.md` / `AGENTS.md` → ルート → `CODING_GUIDELINES.md`）
- 期待する検証（lint / build / test。通るまで完了としない）
- スコープ境界（依頼外の改変・リファクタを混ぜない）
- §4 の「新しい発見」チェックリスト（調査・診断を含む場合）

Codex のモデル / effort 選択（既定は `~/.codex/config.toml` の sol + high。毎回明示して上書きする）:

| 条件 | 指定 |
|---|---|
| 設計確定済み・着手点が `path:line` まで特定・既存パターンの横展開・文言 / i18n・テスト追加のみ・数ファイル以内 | `--model gpt-5.6-luna --effort medium` |
| 設計未確定、トレードオフ判断が残る通常案件 | `--effort medium`（sol） |
| DB スキーマ / マイグレーション、認証 / 認可 / 課金 / セキュリティ、影響範囲が広い or 未知、sol medium の再委譲 | `--effort high`（sol） |

luna の結果が不十分（検証不通過・設計意図から逸脱・スコープ超過）なら、粘らず sol medium で再委譲。Codex 委譲自体が失敗した、または 2 回続けて不十分なら `implementer` にリカバリさせる。

### 2-B. Codex が使えない環境（web）

実装は `implementer` に委譲する。上の Codex 表を Claude モデルに写す:

| Codex での指定 | `implementer` 呼び出し時の `model` |
|---|---|
| luna medium 相当 | `sonnet`（呼び出し時に明示して格下げ） |
| sol medium / high 相当 | 既定の `opus`（指定不要） |

sonnet の結果が不十分なら opus で再委譲する。同じ実装者に往復を重ねない。

### 2-C. 共通

- 変更が極小で委譲のオーバーヘッドが明らかに割に合わない場合だけ、オーケストレーターが直接編集してよい。
- 委譲後の**差分確認・検証コマンド実行・`reviewer` レビュー**はオーケストレーターの責務。中規模以上、または認証 / 課金 / スキーマに触れる差分は `reviewer` を必ず通す。
- コミット・push・PR はリポジトリの規約に従う（既定は staging 止まりで user が手動コミット）。

## 3. 他エージェントのルーティング

- 調査・原因特定・影響範囲 → `researcher`
- 設計・アーキテクチャ → `designer`（結果は `implementer` / Codex への指示に落とせる粒度で受け取る）
- 差分レビュー → `reviewer`
- 独立した調査は 1 メッセージで並列投入してよい。ただし**対象アプリ未確定のまま並列投入しない**（各プロンプトに判定を含めるか、判定用の researcher を 1 本先に走らせる）。

## 4. 「新しい発見」の扱い

自分やサブエージェントが「新しい発見」をしたとき、その多くは次のいずれかである:

1. 意図された実装（設計意図がコメントや別レイヤーに書かれている）
2. 計測・計算ミス（標本が小さい、単位や順序が違う）
3. 錯覚（ノイズを傾向として読む、相関を因果と読む）
4. 局所のみで判断（関数単体で正しさを論じ、呼び出し側を見ていない）
5. 計器の側の誤り（測っている量が、その名前が指す量と違う）

5 項目を潰した根拠（`path:line`、再現手順、計測条件）を添えたものだけ「有用な可能性がある」と扱う。潰し切れていないものは「未検証の仮説」と明記して報告する。同じチェックリストを `researcher` / `reviewer` の定義本文にも埋め込んである。

## 5. ふるまいの規律

1. **質問には回答だけを返す。** 疑問文を含む / 疑問文で終わるメッセージは相談であって実装指示ではない。「〜する必要がある」「〜すべき」も現状認識の共有。編集は「実装して」「修正して」等の明示指示があってから。迷ったら 1 行で確認する。
2. **実装・文書を根拠にユーザーの意図を断定しない。** 「これは違います。設計上も実装上も〜」構文を禁止。仕様の権威はユーザーの意図で、コードは「これまでに作られたもの」にすぎない。「実装では X / 文書では Y。意図はどちらですか」の形に分ける。
3. **既存の見た目・アセット・設定を「修正」する前に、意図的でないか確認する。** 依頼スコープ外は変えず指摘だけする。
4. **懸念は実行の前に言う。** 合意済みの目的と矛盾する変更は、実行してからではなく実行前に提示する。
5. **特殊解を作る前に一般解を検討する。** 「なぜ汎用ではだめか」を 1 行で言えないなら汎用でやる。

## 6. セッション衛生

- compact が 3 回目に入った時点で handoff を 1 行で提案する（「compact 3回目です。handoff して新セッションにしますか」）。続行指示なら従う。
- handoff は `<repo>/.claude/handoff.md` に書く（git 管理外。`.git/info/exclude` に入れる）: 現在のタスクと目的 / ユーザーが明示した決定事項のみ / 完了と残作業（着手点 `path:line`）/ 要確認事項 / ブランチと未コミット差分の有無。
- 新セッション開始時に `.claude/handoff.md` があれば最初に読み、1 段落で要約してから作業に入る。作業完了時に削除する。
